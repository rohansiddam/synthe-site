How Synthe works

You set the bar. Synthe makes your agents reach it on their own.

This page walks the loop end to end: how the bar is set, how changes are proposed and tested, what has to be true before anything merges, and what lands in your repo every morning. The loop runs on any agent, toward any goal your team can state.

Step 5 · Merge clear wins

Before the steps

Any agent. Any goal.

Works on the agent you have

Synthe runs in your repo, against the agent your team already operates: a returns agent, a scheduling agent, a claims agent, an outreach agent. It does not replace the agent or the stack under it. It improves the prompt the agent runs on, one tested change at a time.

Any goal you can state

The bar is whatever your team says good looks like. Some goals are numbers, like a pass rate against your checks. Some are judgment: a tone held, a policy followed, a promise never made. If your team can confirm it in plain language, Synthe can test against it.

The tests improve too

A loop is only as honest as its checks. When a check turns out ambiguous, or the simulated messages drift away from the ones your agent really gets, Synthe revises the checks and the scenarios inside the same loop. The system gets better, and so does the way you judge it.

Set up npx synthe@latest init

One command sets Synthe up in your repo. Your checks and your scenarios live there too, versioned with the code they judge.

Step 1 · E-commerce

Your checks

Everything Synthe does is judged against checks you write and your team confirms.

A check is a plain-language rule about what a good reply does: explain the policy that applies, never approve a refund yourself, never state a delivery date you cannot know. Guardrails are the hard version of the same thing, the rules a reply may never break whatever else it gets right.

There is no grading on vibes. Every simulated reply is marked against these checks one by one, so any score traces back to a rule your team agreed to. And when a check turns out vague, or real messages expose a case it never covered, the loop sharpens the checks as well. The bar is yours. Synthe keeps it honest.

Step 2 · Healthcare

Simulated messages

Before anything is tested, Synthe builds the test: messages like the ones your agent really gets.

The set is written to sound like your actual traffic: the careful portal question, the rushed text message, the phone note with half the details missing. Then it is split in two. The learning set is the one the writer works from. The held-out set stays hidden until scoring, so a change cannot pass by memorizing the questions it was coached on.

Hidden cases go further: your checks applied to messages nobody rehearsed. That is where invented details and quietly broken rules usually surface, so that is where the loop goes looking for them.

Step 3 · Insurance

Propose a change

A writer reads the failures and proposes one small change to your agent's prompt.

Small on purpose. One edit, in one file, aimed at the checks that are failing: a sentence that stops the agent promising an outcome it cannot promise, a line that tells it what to say instead. Nothing else in the prompt moves.

Because each round changes one thing, the test that follows can say whether that thing helped. A big rewrite cannot be judged. A small one can.

Step 4 · Travel

Test the change

The change runs against your checks on both sets, side by side with the prompt you already have.

Every message is answered twice: once by your current prompt, once with the change. The replies are marked check by check, and the two versions are compared head to head, message by message, hidden cases included.

What comes back is not a single score but a shape: where the change wins, where it loses, and whether it broke any rule the old prompt kept. That shape is what the merge gate reads.

Step 5 · Telecom

Merge clear wins

Only a clear win merges, and it merges the way your team already works: a pull request in your repo.

Clear has a definition, not a feeling. The change has to win by more than chance across the set, it has to win on the held-out messages the writer never saw, and it cannot break a single rule that was not already broken. The gate below states all three.

Pass, and the change lands as a pull request with the evidence attached: the scores, the head-to-head record, the rule check. Fail any one condition, and nothing merges. The round is recorded, and the loop tries something else.

The merge gate

Nothing merges on a maybe

Three conditions. All three, every time.

Sign test

The win has to be bigger than chance across the whole set, not a lucky handful of messages that happened to land well.

Held-out win

The change has to win on messages the writer never saw. Passing only the practice set is not passing.

No new rule breaks

One newly broken hard rule stops the merge, whatever the scores say. Guardrails do not trade against points.

Step 6 · Finance

Revert losers

Merging is not the end of the test. A kept change has to keep winning.

Fresh messages keep arriving, and the loop keeps scoring what it kept. If a change that won last week starts losing, or a rule it kept starts breaking, Synthe reverts it on its own and puts the earlier prompt back.

The report says what dropped, when it dropped, and what was restored. A revert is never a mystery, and it never waits for a human to notice first.

Step 7 · The report

The morning report

Every run ends with a report your team can read in a minute, posted where they already work.

The report leads with the number that matters: how often your agent passed its checks. Then the record underneath it: what merged and why, which rounds found no winner, what each round scored, and what it cost.

It is posted in the repo as an issue, next to the pull requests it describes. No dashboard to check and no meeting to schedule: the state of your agent, every morning, in writing.
